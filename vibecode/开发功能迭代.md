# Vibecode 需求迭代工作流

> 在存量项目中做功能迭代时，先理解真实链路，再规划、实施和验证。口头描述、文档与既有实现都可能存在偏差，必须以代码和可执行证据为准。

**Agent Skill：** [skills/vibecode-iteration/SKILL.md](./skills/vibecode-iteration/SKILL.md)（对话中可用 `@` 引用）。详细模板与门禁规则见 [reference.md](./skills/vibecode-iteration/reference.md)；三份文档如有冲突，以 `reference.md` 为 canonical source。

## 一、信息收集与调用链

并行检索并汇总：

- **关键字**：业务术语、模块名、配置项、路由名
- **代码**：入口、核心函数、调用方与被调用方
- **接口**：API 路径、请求/响应结构、网关或拦截器规则
- **文档**：README、架构说明、接口规范、历史方案
- **测试**：单元、集成、E2E 与手工测试记录

基于代码证据梳理 **入口 → 终端汇点（terminal sink）** 的真实调用链，并标注关键依赖、核心分支与职责边界。终端汇点可以是：

- UI render / state
- 持久化
- 外部 API
- 事件发送

选择代码实际支持的终端汇点；行为未写入数据库、缓存或文件时，不得杜撰“落库”步骤。

## 二、上下文校验

**默认假设：用户描述、文档片段和既有实现都可能有误。**

重点校验：

- 描述与代码实际行为是否一致
- 是否存在未记录的分支、兜底或历史兼容
- 是否遗漏跨模块、跨端和上下游联动
- 是否存在权限、加密、缓存、错误处理、并发等边界

将“已确认事实”与“待核实假设”分开记录；边界必须追溯到真实的 `if/else`、guard、matcher、limit 或等价分支。

## 三、迭代规划

计划至少包含调用链摘要、改造步骤、影响范围、依赖、开放问题、测试意图和以下两个**独立维度**。

### 3.1 范围优先级（必须改造 / 可选优化）

| 范围优先级 | 定义 | 具体依据 |
|------------|------|----------|
| **必须改造（Required）** | 为满足用户目标或验收行为必须交付 | 用户明确要求；省略后目标无法达成；目标所需缺陷修复 |
| **可选优化（Optional）** | 延后不会破坏用户目标 | 体验润色；技术债；清理；独立增强 |

### 3.2 风险门禁（高 / 普通）

| 风险门禁 | 定义 | 具体信号 |
|----------|------|----------|
| **高风险（High）** | 真实调用链涉及敏感行为或对外契约 | 持久化数据结构、权限/鉴权、金额、外部接口契约、加密/安全、并发/幂等 |
| **普通风险（Normal）** | 已检查范围内没有高风险信号 | 引用支持该结论的代码或契约边界 |

每个计划项都要分别标注范围优先级和风险门禁，并说明依据。**风险不决定范围：高风险不会自动把可选优化升级为必须改造；普通风险也可能是必须改造。** 无法确定时记录到开放问题，不得用一个维度替代另一个。

优先选择最小、可验证、可回滚的方案，并明确兼容性和延期项的权衡。

## 四、功能对比预期（改代码前）

改代码前输出三部分：可核对的场景假设、带稳定行 ID 的维度表、自拟举例表。`DIM-xx` 与 `EX-xx` 在测试设计和改后对齐中保持不变。

规则：

- “修改前”只能写代码背书的事实，不能把用户叙述或目标行为当现状证据
- 每行都引用真实 `path:symbol` 及已检查分支/查询
- 不变行为也要显式列出
- 举例覆盖命中、未命中和至少一个真实边界
- 每个边界/临界样本都来自调用链追踪发现的真实分支，不得凭空创造

以下仅为格式示例，`illustrative/` 路径不代表当前仓库中的真实文件；实际迭代必须替换为已检查的真实代码位置。

```markdown
### 修改前 vs 修改后

假设：用户生日 `08-15`，当前年份 `2026`，`birthday_noread = 3`。

| 行 ID | 维度 | 范围优先级 | 风险门禁 | 修改前 | 修改后 | 代码/分支证据 |
|-------|------|------------|----------|--------|--------|---------------|
| DIM-01 | 未读开关 | 必须改造 | 普通 | `birthday_noread <= 0` 返回 `[]` | 同左 | `illustrative/birthday_service.go:listBlessings`，early-return guard |
| DIM-02 | 年份 | 必须改造 | 普通 | 查询不限年份 | 仅 `year = 2026` | `illustrative/birthday_repository.go:listLatest`，当前查询无年份条件 |
| DIM-03 | 送礼时间 | 必须改造 | 普通 | 查询不限送礼时间 | 仅 `send_date < 2026-08-16 00:00:00` | `illustrative/birthday_repository.go:listLatest`，当前查询无时间条件 |
| DIM-04 | 条数 | 必须改造 | 普通 | 最新 N 条 | 先筛选，再取最新 N 条 | `illustrative/birthday_repository.go:listLatest`，降序及 `LIMIT N` |
| DIM-05 | 弹窗 / 未读加减 | 必须改造 | 普通 | 现有状态切换 | 不变 | `illustrative/birthday_popup.go:updateUnread`，既有状态分支 |

#### 举例（noread=3）

| 行 ID | 样本 | send | year | 范围优先级 | 风险门禁 | 修改前 | 修改后 | 代码/分支证据 |
|-------|------|------|------|------------|----------|--------|--------|---------------|
| EX-01 | A | 2026-08-10 | 2026 | 必须改造 | 普通 | ✅ 可能进入 | ✅ | `illustrative/birthday_repository.go:listLatest`，年份及时间 true 分支 |
| EX-02 | B | 2026-08-15 23:00 | 2026 | 必须改造 | 普通 | ✅ | ✅ | `illustrative/birthday_repository.go:listLatest`，`send_date < next_day_start` true 分支 |
| EX-03 | C | 2026-08-16 00:00 | 2026 | 必须改造 | 普通 | ✅ | ❌ | `illustrative/birthday_repository.go:listLatest`，`send_date < next_day_start` false 分支 |
| EX-04 | D | 2025-08-10 | 2025 | 必须改造 | 普通 | ✅（若位于最新 N 条） | ❌ | `illustrative/birthday_repository.go:listLatest`，`year == current_year` false 分支 |
```

### 4.1 确认门禁

仅以下组合会阻塞改代码：

- **高风险 + 必须改造**：先展示对比并获得用户确认
- 用户明确要求跳过确认时可以继续，但必须记录该跳过

以下情况不增加确认门禁：

- **普通风险 + 必须改造**
- 任意风险的**可选优化**

可选项永不阻塞实施，高风险也不能把它自动升级为必须项。

## 五、测试设计

先盘点既有测试，标出可复用覆盖和缺口。必须改造范围至少有 P0 主流程与关键异常覆盖；影响范围补充回归用例，并优先采用稳定可复现的自动化。

所有在功能对齐中需要测试证明结论的必须改造 `DIM-xx` / `EX-xx` 行，都至少被一个 TC 通过该 TC 的“关联对比行”字段引用；这包括但不限于边界/临界行。“关联对比行”是测试用例字段，非空值只能是该 TC 引用的 `DIM-xx` / `EX-xx`，测试编号仍保持独立的 `TC-xx`。可选优化或不适用的对比行可以不被任何 TC 引用，但对齐时仍须引用可用的其他证据来源，或明确标记“不适用”。只有不存在对应对比行的 TC，才在其“关联对比行”字段填 `-`。

| 编号 | 场景 | 前置条件 | 步骤 | 预期结果 | 优先级 | 方式 | 关联对比行 |
|------|------|----------|------|----------|--------|------|------------|
| TC-01 | 当前年份正常列表与条数 | 有效生日，noread=3；加载 EX-01 及 E=`07-01`、F=`06-30`、G=`06-20`、H=`06-10` | 请求列表 | A/E/F 按时间降序返回，G/H 不返回，结果共 3 条 | P0 | 自动 | DIM-02, DIM-03, DIM-04, EX-01 |
| TC-02 | 生日当天边界 | 有效生日；加载 EX-02 | 请求列表 | B 被返回 | P0 | 自动 | DIM-03, EX-02 |
| TC-03 | 次日边界排除 | 有效生日；加载 EX-03 | 请求列表 | C 不返回 | P0 | 自动 | DIM-03, EX-03 |
| TC-04 | 往年数据排除 | 有效生日；加载 EX-04 | 请求列表 | D 不返回 | P0 | 自动 | DIM-02, EX-04 |
| TC-05 | 未读开关与状态回归 | noread=0；随后恢复为 3 | 请求列表并验证弹窗/未读切换 | noread=0 返回 `[]`；既有状态行为不变 | P0 | 自动 | DIM-01, DIM-05 |

## 六、实施

通过适用门禁后再实施：

- 列出最小修改文件、符号及每处修改原因
- 保持无关行为和既有契约不变
- 记录兼容、回滚或其他可逆措施
- 可选优化保持非阻塞；延期时记录权衡
- 若用户跳过“高风险 + 必须改造”确认，在改代码前记录跳过

## 七、验证与功能对齐（改代码后）

按设计执行测试、lint、build 或手工检查，并在“测试执行结果”中记录每个 `TC-xx` 的状态（`Pass` / `Fail` / `Blocked` / `Not Run`）、**真实观察结果**及证据/日志。仅代码审查不能推断为 Pass；未执行或无法执行分别记为 Not Run 或 Blocked。

随后复用第四节全部适用的 `DIM-xx` / `EX-xx` 行。功能对齐表必须包含“证据”，引用通过 TC 的“关联对比行”字段关联的 TC ID，以及该 TC 在“测试执行结果”中的状态和真实执行结果。未被 TC 引用的可选或不适用对比行，必须引用其他可用证据或明确写“不适用”；`-` 只属于没有对应对比行的 TC，不能作为对齐行的执行证据。

| 行 ID | 维度 / 样本 | 范围优先级 | 改后预期 | 实际结果 | 结论 | 证据 | 偏差说明 |
|-------|-------------|------------|----------|----------|------|------|----------|
| DIM-01 | 未读开关 | 必须改造 | noread=0 返回 `[]` | 返回空列表 | Pass | 测试执行结果 TC-05（Pass）：noread=0 返回 `[]` | - |
| DIM-02 | 年份 | 必须改造 | 仅 2026 | 2026 保留、2025 排除 | Pass | 测试执行结果 TC-01（Pass）：A/E/F 被返回；TC-04（Pass）：D 未返回 | - |
| DIM-03 | 送礼时间 | 必须改造 | 8 月 15 日包含，8 月 16 日排除 | 边界行为符合预期 | Pass | 测试执行结果 TC-02（Pass）：B 被返回；TC-03（Pass）：C 未返回 | - |
| DIM-04 | 条数 | 必须改造 | 筛选后取最新 3 条 | A/E/F 返回，G/H 未返回，共 3 条 | Pass | 测试执行结果 TC-01（Pass）：A/E/F 降序返回且共 3 条 | - |
| DIM-05 | 弹窗 / 未读加减 | 必须改造 | 不变 | 状态切换与基线一致 | Pass | 测试执行结果 TC-05（Pass）：弹窗和未读切换符合基线 | - |
| EX-01 | A | 必须改造 | ✅ | ✅ 被返回 | Pass | 测试执行结果 TC-01（Pass）：A 被返回 | - |
| EX-02 | B | 必须改造 | ✅ | ✅ 被返回 | Pass | 测试执行结果 TC-02（Pass）：B 被返回 | - |
| EX-03 | C | 必须改造 | ❌ | ❌ 未返回 | Pass | 测试执行结果 TC-03（Pass）：C 未返回 | - |
| EX-04 | D | 必须改造 | ❌ | ❌ 未返回 | Pass | 测试执行结果 TC-04（Pass）：D 未返回 | - |

### 7.1 结论取值

| 结论 | 含义 |
|------|------|
| **Pass** | 已执行证据表明实际结果符合改后预期 |
| **Fail** | 已执行证据表明实际结果不符合改后预期 |
| **Partial** | 已执行证据只满足部分预期，必须写明缺口 |
| **Blocked** | 因依赖、环境、权限或前置条件无法执行验证 |
| **Not Run** | 验证未执行 |

### 7.2 完成判定

- 必须改造行应为 Pass；用户可以书面接受**已观察到的** Partial / Fail 行为偏差
- 相关 P0 必须已执行，并有可接受的真实结果
- 任一必须改造行或相关 P0 为 Blocked / Not Run 时，不得声称完成
- 用户接受可以批准已验证的行为偏差，不能把未执行验证改写为 Pass

## 八、检查清单

### 8.1 执行前

- [ ] 已检索关键字、代码、接口、文档和测试
- [ ] 已梳理入口 → 真实终端汇点及关键依赖，未杜撰持久化
- [ ] 已区分事实与假设，并定位真实分支和边界
- [ ] 每个计划项已独立标注范围优先级与风险门禁
- [ ] 高风险信号仅使用：持久化数据结构、权限/鉴权、金额、外部接口契约、加密/安全、并发/幂等
- [ ] 对比表和举例表使用稳定 DIM/EX ID，Before 与边界均有代码/分支证据
- [ ] 仅“高风险 + 必须改造”已确认，或已记录用户明确跳过
- [ ] 所有需测试证明的必须改造 DIM/EX 行均被 TC 的“关联对比行”字段引用；可选/不适用对比行可不被引用，仅无对应对比行的 TC 填 `-`

### 8.2 完成前

- [ ] 已经过明确实施阶段，并只实施适用门禁后的最小变更
- [ ] 每个设计用例均有测试执行结果，含 TC ID、状态、真实结果和证据/日志
- [ ] 功能对齐复用原 DIM/EX ID，证据引用关联 TC 的执行状态与真实结果
- [ ] 每行结论仅使用 Pass / Fail / Partial / Blocked / Not Run
- [ ] 必须改造行或相关 P0 无 Blocked / Not Run
- [ ] Partial / Fail 仅在用户接受已观察偏差时允许完成，未执行项未写成通过
- [ ] 已检查术语、表格、链接，并运行 `git diff --check`
